# Evals

## Purpose

Evals make the system better when work gets messy.

They should not only score outputs. They should create remediation.

The remediation should usually change an artifact, queue, protocol, template, or failure-mode rule.

## Eval Types

| Eval | Use When | Output |
|---|---|---|
| Handoff eval | A session handoff is created. | Continuity score and fixes. |
| Project-structure eval | Protocols, hierarchy, or operating model changes. | Structural risks and remediations. |
| Artifact-quality eval | A high-stakes memo, thesis, visual, or guide is created. | Quality gaps and changes needed. |
| Release-readiness eval | A repo, essay, or demo is being prepared for sharing. | Data-handling and credibility checks. |
| Public-credibility eval | A repo or artifact should create external trust, network pull, or proof of work. | Clarity gaps, credibility gaps, and changes needed. |
| Continuous-improvement eval | A failure or repeated miss should change future behavior. | Failure log, protocol/template update, and verification. |
| Operating review | A major sprint, correction, or artifact burst happens. | What improved, what is stuck, what needs decision pressure. |

## Rule

An eval is incomplete if it does not answer:

1. What failed?
2. What should change?
3. Which protocol, template, artifact, or queue should be updated?
4. Would a cold reader understand the method without private context?
5. Would the work make a serious founder, builder, or investor want to learn more?
6. What will the agent do differently next time?
